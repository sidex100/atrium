# Тесты браузеров: методика и результаты

[English version](../en/browser-tests.md) · [Установка](install.md) · [Известные проблемы](problems.md) · [Обновления](updates.md)

Как мы меряли плавность видео в Chrome, Chromium и Firefox прямо с бокса, не подходя к ТВ, и что
получилось. Скрипт — `src/tools/atrium-browser-bench.py`.

## Зачем

Пропуски кадров на глаз видно только у ТВ, а цифры YouTube («Статистика для сисадминов») сами добавляют
пропуски и требуют кого-то у экрана. Скрипт делает то же, что человек с пультом: открывает ролик, ставит
4K, разворачивает на весь экран. Потом 30 секунд считает пропуски, нагрузку видеокарты и процессора, а
браузер в это время показывает видео на ТВ как обычно. Каждый вариант браузера или настройки проходит одну
и ту же процедуру, поэтому результаты можно сравнивать.

## Как устроен один прогон

1. Закрыть все браузеры пользователя ТВ.
2. Запустить браузер в сеансе пользователя ТВ (`systemd-run --user -M view@`) с временным профилем и портом
   отладки только на `127.0.0.1`: Chrome и Chromium — протокол DevTools (CDP), Firefox — WebDriver BiDi.
   **Firefox получает свежий профиль на каждый вариант** (ниже, в подводных камнях, — почему).
3. Открыть ролик (4K60 HDR, `SCJxEhG-CZQ`), отклонить окно cookies, пропустить рекламу.
4. Спросить браузер о кодеках так же, как спрашивает сам YouTube (поле `caps`).
5. Попросить у YouTube 2160p, запустить без звука, развернуть на весь экран **нажатием F**: вызов
   `requestFullscreen()` из скрипта браузеры не разрешают, а настоящее нажатие клавиши — разрешают.
6. 15 секунд разогрева (смена качества, переход на весь экран дают пачку пропусков, её не считаем).
7. 30 секунд замера.
8. Сохранить журналы: у Chrome — страницы `chrome://gpu` и `chrome://version`, у Firefox — журнал
   декодеров (`MOZ_LOG`).

В конце скрипт закрывает браузеры и удаляет временные профили (в копии настоящего профиля лежат куки).

## Что измеряется

| Поле | Откуда | Что значит |
|---|---|---|
| `dropped N/M` | `video.getVideoPlaybackQuality()` за 30 с | пропущено кадров из показанных; 60 к/с × 30 с ≈ 1800 |
| разрешение, кодек | `getStatsForNerds()` плеера YouTube | что YouTube реально отдал (`vp09` — VP9, `av01` — AV1, `avc1` — H.264) |
| `hdr`, `fs` | `matchMedia('(dynamic-range: high)')`, `document.fullscreenElement` | считает ли браузер экран HDR; включился ли полный экран |
| `gpu busy` | `/sys/class/drm/card1/device/gpu_busy_percent`, 5 раз в секунду | средняя загрузка видеокарты и доля времени на 95–100 % |
| `browser gfx`, `vcn` | `/proc/<pid>/fdinfo` (DRM fdinfo), по процессам браузера | время видеокарты на рисование и на декодер видео (VCN) |
| `shell gfx` | то же для gnome-shell | сколько видеокарты тратит сборка экрана в GNOME |
| `screen` | `/sys/kernel/debug/dri/1/{state,framebuffer}` | чей буфер на экране и в каком формате (`XR30` — 10 бит, `AR24` — 8 бит) |
| `caps` | `MediaSource.isTypeSupported` и `navigator.mediaCapabilities.decodingInfo` для 4K60 | `ms` — поддерживает; `s`/`m`/`e` — supported / smooth / power efficient |
| `cpu` | `/proc/<pid>/stat` по видам процессов | процессор браузера, % одного ядра |
| `raf` | `requestAnimationFrame` 3 секунды | сколько раз в секунду браузер даёт странице кадр (норма ≈ частоте экрана, 120), самый длинный перерыв, перерывы длиннее 20 мс |

## Как запускать

От root на боксе:

```bash
python3 atrium-browser-bench.py                          # все варианты (долго: ~75 с на вариант)
python3 atrium-browser-bench.py chrome-base firefox-base # только эти
python3 atrium-browser-bench.py firefox                  # все, чьё имя начинается на firefox-
```

Пока идёт тест, мышь и пульт не трогать: браузер на весь экран, ролик без звука. Результаты дописываются в
`/tmp/atrium-browser-bench.txt` (каждый запуск — блок со строкой `===`), журналы Firefox — в
`/tmp/atrium-bench-mozlog/`.

Новый вариант — строка в списке `VARIANTS`: для Chrome третье поле — флаги командной строки, для Firefox —
строки `user_pref(...)` в `user.js` временного профиля.

## Подводные камни

- **Общий профиль портит Firefox.** Firefox запоминает в профиле, насколько плавно шёл каждый кодек, и
  сообщает это YouTube. После одного неудачного варианта YouTube отдавал всем следующим 1080p. Поэтому
  у каждого варианта Firefox свой чистый профиль.
- **Мало кадров — результат недействителен.** Если за 30 секунд показано намного меньше 1800 кадров, ролик
  стоял (буферизация) или YouTube отдал 30 к/с.
- **`fs=n`** — полный экран не включился; такой результат сравнивать с остальными нельзя.
- **YouTube выбирает формат сам.** Один раз Firefox без всяких настроек получил AV1 1080p вместо обычного
  VP9 4K. Смотрите в строке, что именно играло.
- **Пачка на старте** (смена качества, полный экран, у залогиненного — продолжение с места) — поле `start`;
  в замер не входит.
- **«Статистика для сисадминов»** поверх видео сама добавляет пропуски (вариант `chrome-real-auto-stats`).
- **Chrome 136+** не открывает порт отладки на основном профиле: поэтому временный профиль или его копия
  (`chrome-real`).
- **`about:support` Firefox** через порт отладки не открыть — вместо него журнал `MOZ_LOG`.

## Результаты

Бокс: Ryzen 7 7735U, Radeon 680M, Fedora 44, GNOME 50 (Wayland), ТВ 3840×2160 при 120 Гц, масштаб 250 %.

### Chrome и Chromium, 13.10.2026

Рабочий стол тогда был в HDR. На весь экран:

| Вариант | Видео | Пропуски | Видеокарта: средняя / время на 95–100 % | Браузер / gnome-shell |
|---|---|---|---|---|
| `chrome-base` | AV1 10 бит HDR | 4 из 1809 (0,2 %) | 61 % / 52 % | 30 % / 33 % |
| `chrome-overlay` | AV1 HDR | 3 из 1807 (0,2 %) | 65 % / 55 % | 32 % / 36 % |
| `chrome-nohdr` | VP9 SDR | 2 из 1810 (0,1 %) | **13 % / 7 %** | 5 % / 18 % |
| `chromium-base` | AV1 HDR | 4 из 1808 (0,2 %) | 61 % / 54 % | 28 % / 31 % |
| `chrome-real-auto` | AV1 HDR | 8 из 1805 (0,4 %) | 78 % / 69 % | 56 % / 30 % |
| `chrome-real-auto-stats` | AV1 HDR | 9 из 1807 (0,5 %) | 77 % / 73 % | 58 % / 33 % |

В окне: `chrome-zerocopy` и `chrome-overlay-zerocopy` — 4–5 из ~1810 (0,2–0,3 %), как без них;
`chrome-vulkan` — VP9 декодирует процессор (VCN 0 %), **545 из 1817 (30 %)**.

**Вывод.** В HDR Chrome рисует кадр в 16-битном формате, а GNOME заново собирает весь экран в HDR:
видеокарта половину времени загружена на 95–100 %. Без HDR — 13 %. Флаги не помогают, Vulkan ломает
аппаратный декодер. **Решение:** рабочий стол в SDR, HDR только для фильмов в mpv (установка, шаг 9,
«Авто-HDR»).

Декодер видео (VCN) во всех вариантах с VP9 4K — около 50 %, в журнале `MOZ_LOG`: VA-API, кадр 4K за 0,45 мс.
Во всех вариантах `caps` — `ms/sme`: Firefox сообщает, что VP9, AV1 и H.264 в 4K60 играет плавно и экономично.

**Вывод.**
- кодеки и ffmpeg ни при чём: декодирует видеокарта и с огромным запасом;
- AV1 YouTube Firefox не отдаёт: без VP9 получается H.264 1080p, поэтому расширения вроде
  enhanced-h264ify не помогают;
- WebRender и так на видеокарте (программный — 3 ядра и 87 % пропусков);
- **виновата синхронизация с экраном:** кадры от GNOME на Wayland приходят неровно (86–91 в секунду
  вместо 120). Своим таймером 120 Гц Firefox рисует ровно, и пропуски уходят.

**Решение:** политика Firefox `widget.wayland.vsync.enabled = false`, `layout.frame_rate = 120`
(`/etc/firefox/policies/policies.json`, установка, шаг 9; подробнее — «Известные проблемы», «Пропуски
кадров в Firefox»).
